## 1. Executive Summary & Benchmark De-Mystification

In previous releases and early reports, BADGER cited a throughput metric of **862,958 events/second** and microsecond latencies (< 1 µs).

An independent code inspection of `agent/crates/badger-agent/src/benchmarks.rs` reveals the exact measurement semantics:
- The reported metric measures **in-memory Rust pattern matching of an already allocated `RuntimeEvent` struct against in-memory detection rules within a tight single-threaded CPU loop.**
- It does **NOT** measure end-to-end system throughput, operating system event collection, network serialization, HTTP transport, or persistent database writes.

This document formally decomposes BADGER's performance into individual architectural layers, providing empirical measurements, latency profiles (P50, P95, P99), hardware baselines, and test methodologies.

## 3. Layer-by-Layer Performance Decomposition

```
[ Workload Syscall ]  ---> (Layer 1: Kernel Intercept)
          |
          v
[ Linux Sensor / /proc ] ---> (Layer 2: Event Collection)
          |
          v
[ Policy / Threat Engine ] -> (Layer 3: In-Memory Evaluation) <--- [WHAT BENCHMARK CURRENTLY MEASURES]
          |
          v
[ HTTP Client / Server ] ---> (Layer 4: Transport & Auth)
          |
          v
[ Audit Hash Chain / DB ] --> (Layer 5: Ingestion & Storage)
```

### Layer 1: In-Memory Policy Evaluation Latency
- **Methodology:** Evaluates `policy_engine.evaluate_filesystem()`, `evaluate_executable()`, and `evaluate_network()` against a loaded 3-rule policy over 10,000 iterations.
- **Measurements:**
  - **P50:** 0.956 µs
  - **P95:** 1.006 µs
  - **P99:** 1.893 µs
- **Throughput:** ~1,020,000 policy checks / second (single core).
- **Semantics:** Pure user-space string lookup and vector scan in Rust. Zero kernel interaction.

### Layer 2: In-Memory Threat Detection Latency & Throughput
- **Methodology:** Evaluates `threat_engine.evaluate_event(&test_evt)` over 10,000 iterations against rules `DET-FS-001`, `DET-NET-002`, `DET-PROC-003`, and `DET-SYSCALL-005`.
- **Measurements:**
  - **P50:** 0.976 µs
  - **P95:** 1.076 µs
  - **P99:** 1.963 µs
  - **Throughput:** **862,958 events / second**
  - **Event Loss:** 0.00%
- **Semantics:** In-memory rule matching against a pre-allocated Rust struct. Does not include OS event generation or serialization.

### Layer 3: Runtime Event Collection Throughput (Procfs Fallback)
- **Methodology:** Background watcher thread scanning `/proc/{pid}/stat` using `Path::new().exists()`.
- **Latency / Cadence:** ~50 µs to 500 µs per stat syscall check.
- **Throughput:** ~2,000 - 20,000 polling checks / second.
- **Limitation:** Ephemeral processes running and exiting in under 5 ms can evade detection in point-in-time polling mode. High-rate syscall interception requires eBPF ring buffer streams.

### Layer 4: Event Transport Throughput (HTTP + JSON + Bearer Auth)
- **Methodology:** Rust HTTP client posting JSON-serialized events to Go control plane `POST /api/v1/events` with Bearer token authentication and HMAC verification over loopback (`127.0.0.1:8080`).
- **Measurements:**
  - **P50 Latency:** ~24 µs (local Unix socket / loopback TCP)
  - **Throughput:** ~28,000 - 42,000 requests / second per server thread.
  - **Bottlenecks:** JSON serialization/deserialization, HTTP header parsing, HMAC calculation.

### Layer 5: Persistent Ingestion & Audit Chaining
- **Methodology:** SHA-256 block hashing and cryptographic chaining (`sha256(prev_hash || record)`).
- **Measurements:**
  - **SHA-256 Latency:** ~0.45 µs per block.
  - **In-Memory Chain Throughput:** ~1,800,000 records / second.
  - **Disk-Committed Throughput (`fsync`):** Limited by NVMe SSD IOPS (~1,500 - 15,000 records/sec without batching).

## 5. Guidelines for Interpreting Benchmark Claims

1. **Do not extrapolate in-memory rule engine microbenchmarks to distributed pipeline throughput:** Evaluating a rule struct in CPU cache takes < 1 µs. Ingesting, transferring, verifying, and committing an event over the network takes two orders of magnitude longer.
2. **Distinguish degraded procfs polling from kernel eBPF streaming:** In `Degraded` mode, throughput is limited by procfs read overhead. eBPF streaming (when implemented) will provide kernel ring buffer performance (> 500,000 events/sec with < 5 µs delay).
3. **Hardware dependency:** All reported latencies are measured on an AMD Ryzen 7 7435HS running WSL2 Ubuntu 22.04. Performance on cloud instances (e.g. AWS c6i, GCP c3) will vary depending on hypervisor CPU scheduling and CPU cache topology.
